# 永豐真實下單驗證手冊

用途：把「開盤前要確認什麼、09:10 後怎麼驗證、成功要留哪些證據、失敗怎麼檢討、改碼後怎麼重驗」固定下來，避免之後改了一堆代碼又忘記怎麼核對。

最後更新：2026-04-25 上游預選 10:00 確定規則 Asia/Taipei

## 適用範圍
- 這份手冊主要用在目前受 guard 的真實下單路徑：`2330 / Buy / IntradayOdd / 1股 / 09:10 / price cap 2100`
- 這份手冊也同時區分 上游預選主線與 guard 單股主線，避免把兩者混在一起看。
- 上游預選主線目前固定從 `<WORKSPACE>\data\private_preselect_export\*.json` 找來源。
- 上游預選主線只吃 `target_trade_date` / `source_target_trade_date` 對準目標交易日的 `a_preselect`。
- 上游預選主線若找不到 target 對準目標交易日的 上游預選就直接 `pass`。
- 上游預選確定 / materialization 固定在目標交易日 `10:00 Asia/Taipei` 之後才允許執行。
- 操作提醒固定句：`10點後才會執行永豐自動交易的確定上游預選工作。`
- guard 的 `2330` 單股排程與 上游預選主線是分開的；上游預選缺檔，不等於 `2330` 單股排程失敗

## 驗證目標
- 開盤前先確認：排程會不會跑、券商登入是不是 live-ready、今天主線預期到底是 `pass` 還是會產生 basket 名單
- 09:10 後確認：到底有沒有真的送出委託、是否能在永豐手機端看到單、是否留下 task log / artifacts
- 成功時留證據：之後改碼還知道什麼叫「成功」
- 失敗時留證據：之後回頭檢討不會只剩一句「今天沒下到」

## 一、開盤前固定確認
建議在交易日早上 `09:00` 前做完，但只做只讀檢查，不做 上游預選正式 materialization。

   - 也可以檢查其他日期檔案內的 `target_trade_date` / `source_target_trade_date`
   - 有 target 對準檔案：表示 10:00 後可以做 `prepare_week` / `finalize`
   - 沒有 target 對準檔案：表示 上游預選主線今天應該 `pass`，這是正常結果，不是故障
   - 10:00 前即使有檔案，也不要把它 finalize 成正式買進清單

2. 確認 Windows 工作排程是否 ready

   - 預期只有 guard 的 `2330` 單股排程會動
   - 上游預選整包主線今天應該是 `pass`
   - 若 target 對準的 上游預選存在：
   - 10:00 後才可執行確定 上游預選、`finalize` 與後續 basket buy
   - 但這不代表已自動授權 live basket；仍要分清楚目前有沒有明確 live 授權

## 一之一、為什麼 上游預選要等 10:00
- 週一早上 06:00 才開始執行預選名單的產出，所以 09:00 開盤附近最新名單可能還沒產完。
- 我們很可能在週一開盤之前做永豐自動交易測試；若測試時就允許 `prepare_week` / `finalize`，可能會把週末已存在的 上游預選檔物化成週一正式買進名單。
- 週末產出的檔案即使標到週一，也不是週一早上 06:00 流程跑完後的最新結果。
- 因此 10:00 前只做只讀檢查；10:00 後才執行永豐自動交易的確定 上游預選工作，並重新產生當天 `sizing.csv`。

## 四之一、已授權整包 live 買進失敗後怎麼做
- 這套流程適用所有未來整包 live 買進，不只 2026-04-27，也不只某一次週一。
- `buy_loop --live` 若被 live gate 擋住、broker 回 failed / rejected / error、單列 blocked、或目標股數未完整送出，會寫入 `repair_confirmation_required`。
- 下單失敗時，先修復 blocking issue，但修好後不能直接續下。
- 修復後必須先跑：
```powershell
python run.py repair_confirmation --trade-date YYYY-MM-DD --live --email-to ops@example.com
```
- 報告必須列出：
  - 買了什麼 / 已成交
  - 已送但未完全成交
  - 什麼還沒買 / 尚未送出
- 用 Gmail 把報告寄給使用者後，必須查同一封 mail thread 的回覆。
- 使用者不需要固定制式回覆；依回信具體內容判斷，例如同意補下全部剩餘、只補某幾檔、不同意補下、或先停住。
- 只有回信內容明確授權，且仍是原本授權交易日 / 第一交易日，才可補下符合回信範圍的「尚未送出剩餘單」。
- 若回信不同意、要求先停、內容不清楚、範圍對不上報告、或要求補已成交 / 已送等待成交 / 狀態不明項目，停止並回報。
- 接著下之前，必須先確認 broker 端與本地 artifacts 都沒有不明狀態：
  - 沒有 ambiguous fill
  - 沒有可能已送出的未知委託
  - 沒有同 strategy lot 的 active order 會造成重複買
  - 沒有 broker / local 持倉或成交矛盾
  - 週預算、上游預選來源、`sizing.csv`、live gates 沒有在修復過程中改成另一個版本
- 「不重複買到」優先於「補下剩餘單」；只要 broker 或 local 任一邊顯示同一個 strategy lot 已有 active / filled buy，就必須視為已有曝險，不能再送同一筆。
- 重送前必查重複買來源：
  - 本地 `orders.csv` 的 `strategy_lot_id` / `order_id`
  - 本地 `positions.csv` 與 week lot ledger 的 `buy_fill_qty` / `closing_qty`
  - broker fills
  - broker active orders by `order_id`
  - broker orders by deterministic `broker_custom_field`
- 如果已經不是原本授權交易日 / 第一交易日，就停止，不把週一失敗延伸成週二或週三追買。
- 程式本體目前有 `repair_confirmation_required` 與對帳 report；Gmail thread 查詢與依回信內容續下目前由 Codex/自動化流程執行，尚未做成本體硬 gate。

## 五、常見判讀方式
- 沒有 target 對準目標交易日的 上游預選來源：
  - 代表 上游預選主線今天應該 `pass`

- Windows task `Ready`，但 `09:10` 後手機端沒看到單：
  - 先查 task log
  - 再查 `post_guarded_order_check`
  - 再決定是不是 runner / broker / guard 問題
- 手機端看得到單，但 `fills.csv` 還沒東西：
  - 可能只是尚未成交

- `positions.csv` 空白：
  - 若尚未成交，這是正常
  - 若已成交還是空白，才要查 reconcile / accounting / excluded scope

## 八、2026-04-24 事後檢討紀錄
這段是 2026-04-24 實際沒有下到 `2330` guard 單後補進來的固定檢討。以後遇到類似狀況，先照這裡比對，不要只看「排程 Ready」就以為一定會送單。

### 1. 當天預期
- 受 guard 的單股真實下單路徑：`2330 / Buy / IntradayOdd / 1股 / 09:10 / price cap 2100`
- 預期行為：`09:10` 後 runner 啟動，若 live guard 全部通過，才進入 chase 下單。
- 上游預選整包主線：同日 A 檔於當天出現後可以 materialize，但 2026-04-24 是本週最後交易日，整包 `buy_loop` 規則不再開新買單。

### 2. 真正根因
- `09:10` 排程時間到時，`config/auto_trading.yaml` 的 `auto_trading.live_enabled` 尚未打開。
- `live_enabled` 是在 `2026-04-24 11:18:15 +08:00` 才修好。
- 這個時間晚於 `2026-04-24 09:10:00 +08:00` 的排程執行時間，所以當天那次受保護下單被 live guard 擋下。
- 系統規則是：錯過的真實下單不自動補單，除非屬於同一次已授權的週一 / 第一交易日整包買進，且修復後仍是同一個第一交易日、broker/local 狀態完全明確。

### 3. 這次不是什麼問題
- 不是永豐 CA 到期。
- 不是股票帳號未簽署。
- 不是 上游預選沒有來源。
- 不是單純 Windows task 沒 Ready。
- 不是應該自動拿 4/23 的 A 名單來補下 4/24 的單；同日 A 規則禁止沿用前一天。

### 4. 以後下單前必查清單
在 `09:10` 前，至少要同時確認：
- `SINOPAC_ALLOW_LIVE_SUBMIT=1`
- `AUTO_TRADE_LIVE=1`
- `config/auto_trading.yaml` 裡 `auto_trading.live_enabled=true`
- runner 腳本有設定 `AUTO_TRADE_LIVE=1`
- Windows task 是 `Ready`
- `Next Run Time` 還沒過
- runner smoke test 通過
- `login-check --live --no-fetch-contract` 顯示股票帳號 `signed=True`

### 5. 事後固定判讀規則
- 如果 `config_last_modified` 晚於 `task_recorded_at` 或晚於排程時間，代表設定是在排程後才修好，該次下單不能算成功。
- 如果 `post_guarded_order_check.json` 顯示 `live_enabled_fixed_after_scheduled_run`，結論就是：保護條件已修好，但當天排程時間已過，不會補單。
- 如果 `today_new_order_submission_status=no_auto_new_buy_paths_remaining_today`，代表今天已沒有自動新買單路徑可送出。
- 如果 `positions.csv` 沒有策略部位，`sell_loop_readiness` 應該顯示沒有可賣的策略部位，不應硬送賣單。

### 6. 這次已經補進系統的證據鏈
之後不用靠人工記憶，應直接看這些檔案：

2026-04-24 之後，上面這些檔案應該會直接寫出：
- `config_timing_status=live_enabled_fixed_after_scheduled_run`
- `config_last_modified=2026-04-24T11:18:15+08:00`

- 結論：保護條件問題已修好，但今天排程時間已過，不會補單。

### 7. 以後不能再犯的錯
- 不能只看 Windows task `Ready` 就說「明天一定可以下單」。
- 不能忽略 `auto_trading.live_enabled`。
- 不能把「修好設定」和「當次排程已經成功送單」混為一談。
- 不能把整包 上游預選主線和 `2330` guard 單股主線混在一起判斷。
- 不能在排程時間過後偷偷補真實單；例外只限同一次已授權的週一 / 第一交易日整包買進，且修復後仍在當日、沒有任何重複下單或狀態不明風險。
- 不能只因為本地沒有 `orders.csv` 就認定沒送單；必須用 broker `custom_field` / `order_id` / fills 再查一次，避免本地漏寫造成重複買。
